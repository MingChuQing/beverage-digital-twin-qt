# DeepSeek → JSON → 三道关口 → 串口 / 3D

## 现场操作

1. 两根 USB/TTL 线按原接线方式互接。双击 `run_ai_demo.bat`：接收端 COM10、发送端 COM3，115200 / 8N1。默认从三口味、两规格的原配置开始。
2. 发送端默认打开“AI 配置生成 · 论文演示”。填写 DeepSeek Key，或在启动前设置进程环境变量 `DEEPSEEK_API_KEY`。Key 以密码框显示，点击生成后清空，不写入 JSON、命令行、设置或日志。模型默认 `deepseek-flash`，可填写账号支持的其他 DeepSeek 模型。
3. 使用默认中文需求，或用自己的说法描述同一现场案例：三种口味同时增加250mL小瓶装、两批每批六瓶、保持原六配方，使用预置工程坐标。
4. 点击“生成 JSON 并验证”。界面显示轮数、原始 JSON 和每个实际验证结果。JSON 不合格时，将实际错误发回 DeepSeek，请它重新输出完整增量，重新检查全部关口。最大轮数可设1–6；达到上限、网络故障、取消或工具故障均停止，保留原配置。重试可发起新会话。
5. 两个自动关口通过后，查看“配置文件差异”和“语义审核说明”。核对需求和上瓶/容器/成品点位，勾选两项后点击“人工审核通过并应用”。失败候选没有应用按钮。首次直接通过时，如实显示一次通过。
6. 选择口味和规格。PPT可选择“首瓶片段”，点击“串口执行 → 3D”；需完整论文写序列时选择“完整12瓶”。此时串口写指令取自刚验证的候选JSON轨迹，3D接收真实串口指令变化。
7. “查看演示记录”打开本次会话目录，可展示原始输出、API实际模型/Token统计、每轮错误、C++输出、仿真报告、完整双解释器轨迹、差异和审核记录。记录默认在 Windows 用户应用数据目录 `IndustrialConfigEngine/BeverageTwinDemo/ai-sessions` 下，源码和原论文案例不被覆盖。

两个程序在同一电脑上共享审核后原子保存的配置激活记录。接收端在收到串口配方选择时核对报告、审核与候选文件哈希，加载同一份候选；因此即使AI追加点位的编号顺序不同，3D点位卡片也与本次JSON一致。运动、阶段和反馈仍通过串口获取。跨电脑使用需另行分发候选配置，本版不提供远程配置传输。

## 与论文流程的对应

| 环节 | 当前实现 |
|---|---|
| 自然语言输入 | 中文需求 + 冻结工程上下文；输入是原六配方，没有把新增配方答案提供给模型 |
| DeepSeek生成 | HTTPS调用官方 `/chat/completions`；JSON输出模式；原始内容逐字节保存；记录实际服务模型名 |
| 第一关 | 原增量白名单/工程约束检查 + 原C++解析/结构检查和9个入口的虚拟执行 |
| 第二关 | 原Python双解释器比较完整时序；9个正常配方、11个既定故障；原6配方与重新执行基线一致 |
| 失败修正 | 原始错误 → 模型 → 完整新增量 → 从原基线重新验证；工具/网络故障不会假装成配置缺陷 |
| 第三关 | 操作者查看差异、核对语义后审核应用；AI没有直接部署权限 |
| 应用与展示 | SHA-256绑定候选与轨迹；修改后必须重新验证；Qt加载候选、通过COM3发送至COM10 |

本版有明确范围：**只支持论文中的三口味新增250mL案例**。容量、流量、设备和点位均为预先给定数据，不接受AI猜测物理标定，不是任意生产线的自由编程界面。

完整自动验证保留原十二阶段、两批六瓶、全部原虚拟工艺时长。为PPT回放，除运动和灌装外的等待加速50倍；首瓶片段只包含初始化、第一瓶、CIP和回零，实际出料计数为1。串口发送逐条校验应答，反馈为虚拟设备计算。**当前串口部分是已验证写轨迹回放，没有实现原配置引擎的在线条件解释**。它不能证明实机过程控制、灌装精度或卫生效果。

故障回归只作用于原配方索引0；不声称九个配方逐一覆盖所有故障。自动化界面测试中的审核明确记为 `TEST_ONLY`，不充当人工语义审核证据，正常回放不接受该记录。

## 构建与测试

Qt仍为5.14.0/MinGW7.3。AI编排使用Python标准库，随部署目录附带运行时，无需安装pip包。构建时另需现有Python3.12和C++17工具链编译原引擎探针；本机可用已有的Zig。

```powershell
.\build_demo.ps1 -Deploy -PythonExecutable 'C:\Python312\python.exe' -AiCompiler 'C:\tools\zig.exe'
python tools/test_ai_pipeline.py
```

`test_ai_pipeline.py` 明确使用本地HTTP mock制造第一轮错误、第二轮修正；执行真实验证器，检查冻结层、路径限制、重复JSON键、无审核禁用、测试审核不能部署以及校验后篡改的拒绝。它不调用真实DeepSeek，也不把人工注入错误伪装成AI错误。

真实调用（从环境变量读Key；报告在忽略的build目录）：

```powershell
python tools/live_ai_check.py
```

拿到真实调用生成的 `round-01/report.json` 后，可运行两个原生界面和实体USB/TTL集成测试：

```powershell
python tools/verify_ai_serial.py --report '实际路径\round-01\report.json' --receiver-port COM10 --sender-port COM3
```

此测试复制独立候选、操作审核控件并标记 `TEST_ONLY`，不会把它保存成真实人工审核，也不修改真实调用记录。普通历史回看可使用 `BeverageTwinDemo.exe --sender --ai-report '报告路径'`；界面会标注历史记录，需要本次人工审核，不冒充新生成。

来源、冻结输入和方法边界见 [`ai/NOTICE.md`](../ai/NOTICE.md) 与 [`ai/provenance.json`](../ai/provenance.json)。
